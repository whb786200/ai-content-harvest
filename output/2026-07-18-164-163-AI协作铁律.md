# 工程人玩转AI的两条铁律：把决策交给代码，把目标交给AI

> 本文基于 SKILL.md #164（2026提示词工程CREATE框架）+ #163（AIHOT热点监控系统架构）扩写
> 蒸馏日期：2026-07-18

---

上周我用AI整理一份5000行的项目验收清单，想让它"按规范整理"。

结果它给我交了一段抒情散文。问题出在哪？我告诉它"做什么"，却没说清"做到什么算好"。

这不是AI的错，是我没把"目标"说清楚。再往深处想，我其实犯了两个老毛病：

- **管得太细**：想一步步指挥AI，结果它反而迷路
- **甩得太粗**：只给目标不给标准，结果它自由发挥

这两个毛病，恰好对应了2026年AI协作的两条新原则。

今天拆给你看。

---

## 一、第一条铁律：把"指挥AI"换成"委托AI"

2026年提示词工程最大的变化，不是技巧升级，是**范式翻转**。

旧范式（2023-24）：过程控制。写Prompt像写SOP——"第一步、第二步、第三步"。每一步都恨不得手把手。

新范式（2026）：结果定义。你只需要说清楚"目标是什么、成功标志是什么"，让AI自己规划路径。

OpenAI 官方在2026年的提示词指南里给了一句话：

> **"Trust the model's judgment. Define success, not process."**
> 信任模型的判断。定义成功，而非过程。

工程人对这句话应该有共鸣——我们做项目管理也是这套逻辑：跟分包单位说"这堵墙要达到验收标准"，而不是"先砌三行再抹灰再压光"。

但问题来了：怎么定义"成功"才不模糊？

### CREATE 框架（2026升级版）

CREATE 是一个把"目标描述"拆成5个维度的工具，专门解决"说不清标准"的问题。

| 要素 | 说明 | 2026新变化 |
|------|------|-----------|
| **C - Context** | 告诉AI"你是谁" | 新增：明确"能力边界" |
| **R - Request** | 清晰的任务指令 | 新增：定义"成功标准"而非步骤 |
| **E - Examples** | 1-3个输入输出示例 | 新增：多模态示例 |
| **A - Adjustments** | 格式/字数/禁止事项 | 新增：输出验证机制 |
| **T - Tone/Test** | 输出风格语调 | 新增：思考过程展示程度 |

落地时直接套这个模板：

```
【角色】你是一位拥有10年经验的[专业角色]
【边界】不确定时标注"需要人工确认"
【任务】请完成[具体任务]
【成功标准】完成的标志是：[可验证标准]
【输出格式】严格按格式输出
【验证要求】输出前自我检查：[检查清单]
```

### 一个真实例子

你想让AI帮你审核施工方案，传统Prompt可能是：

> "请按规范审核这份方案。"

按 CREATE 改写：

> 【角色】你是一位注册安全工程师
> 【边界】规范条款有歧义时标注"待确认"
> 【任务】审核这份《深基坑专项施工方案》
> 【成功标准】输出包含：①不符合规范的条款及依据 ②风险等级（高/中/低）③修改建议
> 【输出格式】Markdown 表格，列：条款编号 / 风险描述 / 规范依据 / 修改建议
> 【验证要求】输出前自检：是否漏掉危大工程条款？是否引用了过期规范？

这两段Prompt的输出质量差距，你试试就知道。

## 二、第二条铁律：把"AI决策"换成"代码决策"

讲完提示词，再讲个更深的问题：什么时候该让AI判断，什么时候该让代码判断？

看一个反例。

卡兹克做AIHOT热点监控系统，前10版一直在Prompt里加规则："这个信源权重高、那个信源权重低"、"硬核论文给90分、鸡汤给80分"。结果系统越来越蠢——硬核论文和鸡汤得分经常倒挂。

第11版，他做了一个关键改动：

```
模型 → 只做5维打分（不做决策）
代码 → 信源权重、类型权重、聚类、最终排序（代码管所有决策）
```

11版迭代验证的最终方案是：**能用代码处理的，就不用模型**。

工程人应该秒懂这个道理——

- 钢筋间距不达标 = 代码规则判断（GB50204，第5.4.1条，±10mm）
- 安全隐患照片分类 = 模型判断（视觉理解）
- 月度产值报表汇总 = 代码规则判断（Excel公式）
- 危大工程方案可行性评估 = 模型判断（需要经验）

把"决策"和"判断"分开：

| 任务类型 | 适合谁 | 原因 |
|----------|--------|------|
| 规则明确、有标准 | 代码 | 0误差、0成本、可审计 |
| 模糊、需要经验 | 模型 | 灵活、可处理长尾 |
| 大规模重复 | 代码+模型混合 | 模型分，代码合 |

**核心原则：能用代码兜底的，绝不让模型拍板。**

这是工程人用AI最容易踩的坑——以为"AI全包"就是"先进"，结果幻觉和错误率让你怀疑人生。

## 三、工程人落地三条清单

讲完两条原则，给三条马上能用的清单：

**1. 下次写Prompt前，先写"成功标准"**

不要直接开写。先问自己：这件事做到什么程度算"完成"？能不能用一句话写出来？

写不出来，说明你还没想清楚，那就别让AI开干。

**2. 把能写规则的步骤，拆给代码**

项目管理、报表统计、规范校核——只要标准是明确的，全部用脚本/公式实现。AI 只在"经验判断"环节介入。

**3. Prompt 里强制加"验证清单"**

不管任务大小，Prompt 末尾加一段"输出前自检"。这是控制幻觉最便宜的一招。

## 写在最后

AI 不会替代工程人，但用 AI 的工程人会替代不用 AI 的工程人。

但前提是：你得用对地方。**把目标说清楚，把决策交代码，把判断留给人。**

这是工程人区别于"普通用户"的核心——我们懂标准、懂边界、懂什么叫"做不到就是做不到"。
