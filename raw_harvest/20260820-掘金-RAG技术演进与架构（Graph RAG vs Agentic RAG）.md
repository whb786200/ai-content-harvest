# RAG技术演进与架构：从Naive RAG到Graph RAG与Agentic RAG

> **来源**: 掘金 (https://juejin.cn/post/7675686590932484137)
> **日期**: 2026-08-20
> **主题**: RAG技术演进、Graph RAG、Agentic RAG架构对比与落地降本

## 1. 演进总览：从Naive RAG到下一代架构

### 1.1 传统RAG（Naive / Vector-based RAG）

传统RAG是一条单向、静态、写死的硬编码流水线：用户提问 → Embedding向量化 → 向量相似度检索(Top-K切片) → 拼接Prompt → LLM单次生成

### 1.2 传统RAG的核心硬伤

1. **"只见树木，不见森林"**：向量检索只能命中局部的具体片段。当遇到宏观归纳类问题时，没有任何单一文本块包含完整答案，导致检索失效。
2. **"一次性被动检索"**：无论检索到的文档是否相关，系统都会无差别喂给大模型；若检索质量差，大模型只能"幻觉瞎编"或直接拒答。
3. **数据源单一**：只能处理非结构化文本的切片，无法有效关联结构化数据(SQL)、复杂关系网络(图谱)或实时外部信息(Web)。

### 1.3 核心洞察：下一代RAG的"成本时空转移"哲学

两者的本质差异在于把巨大的算力与Token成本花在哪个阶段：
- **Graph RAG是"重建库、轻运行"**：成本堆在前期建库阶段(Indexing Time)，建图极其昂贵，但建好后查询相对直接。
- **Agentic RAG是"轻建库、重运行"**：建库阶段与传统RAG一样便宜，但每次请求的运行时(Runtime/Query Time)消耗大量Token和延迟。

## 2. Graph RAG：知识图谱增强检索与落地降本方案

核心思想：改变知识的组织结构——将扁平的文本块升级为"实体-关系"知识图谱与多层次社区摘要。

### 2.1 核心优势

- **宏观归纳与全局问答(Global Search)**：通过预先生成的"社区层级摘要"，快速对海量文档的主题、趋势进行宏观概括。
- **多跳关系推理(Multi-hop Reasoning)**：通过图谱中的关系链路(A→B→C)，轻松解答跨实体、跨文档的复杂关联问题。

### 2.2 核心劣势与挑战

- 建库成本极高(Token & 费用黑洞)：抽取实体、关系、实体消歧以及生成全量社区摘要需消耗海量LLM Token。
- 增量更新困难：新增或修改文档会破坏原有的图拓扑和社区划分，可能导致局部甚至全量摘要需推倒重算。
- 简单问题性价比低(Overkill)：对简单的点对点事实查询，图遍历耗时更长且成本远高于普通向量检索。
- 图数据库运维门槛高：Neo4j、NebulaGraph等的部署、Cypher编写和性能调优对工程团队要求高。

### 2.3 工业级落地降本与优化方案

#### ① 非全量图化（局部建图 / 核心领域图化）
- 按Schema定向抽取：预先定义核心实体类型，非相关实体直接过滤。
- 高价值文档图化：只对总结性文档、核心业务文档、实体密集型文档建图。

#### ② 实体消歧与低成本对齐
- 小模型NER + 规则词典优先：先用轻量级本地NER模型配合业务词典进行初步实体提取与同义词映射。
- 向量聚类消歧：对语义相似度高于阈值的候选实体，仅在必要时才调用轻量LLM进行判定合并。

#### ③ 增量更新与局部重构
- 局部子图更新：新文档只与当前局部图节点做关联，只更新受影响的最小子图社区摘要。
- 分层缓存：对高频访问的顶层社区摘要进行持久化缓存，夜间批量执行异步图拓扑微调。

#### ④ 混合检索与动态分流
- 系统默认走"向量检索 + BM25关键词 + Reranker"（低成本、低延迟）；只有识别出用户意图是"全局总结型"或"复杂关系多跳型"时，才触发Graph RAG引擎。

## 3. Agentic RAG：智能体驱动的动态检索与编排

核心本质：
1. 本质就是一个编排了多工具的Agent：被赋予多种检索工具（SQL、向量数据库、网页搜索引擎、图数据库）的AI Agent，通过LangGraph状态图框架编排业务流程。
2. 本质上只是把成本堆到了运行时(Runtime Cost)：建库阶段几乎无额外成本，但每次在线用户提问都在反复消耗大模型推理Token和时间延迟。

### 3.1 为什么必须用LangGraph编排

检索过程是一个带循环的状态图(StateGraph)：
- **条件分支(Conditional Edges)**：根据大模型判断结果，决定下一步走哪个节点。
- **循环自纠(Cycles)**：如果评估节点发现检索评分低于阈值，流程循环返回到改写节点，重新发起检索。
- **状态持久化(State Persistence)**：全局状态在节点之间顺畅流转。

### 3.2 核心模式总结

- **Router RAG(动态路由)**：大模型充当"交警"，把问题分发给最合适的数据源。
- **Corrective RAG(CRAG，纠错式RAG)**：增加文档质量判定环节，检索质量低时自动触发关键词改写或网络搜索降级。
- **Self-RAG(反思式RAG)**：在生成后反查引用源，自动消除幻觉。
- **Multi-step Reasoning(多步拆解)**：将复合大问题拆解成子问题依次检索。

### 3.3 核心劣势：运行时成本与高延迟

- 在线查询延迟极高：多次LLM往返，单次问答通常耗时10~30秒以上。
- 单次查询费用成倍上升：Token是传统RAG的5~10倍。
- 死循环与错误级联风险：若反思阈值过高可能导致反复改写陷入死循环。

### 3.4 工业级落地降本与低延迟优化方案

1. **大小模型协同**：小模型负责耗时但结构固定的节点(Router分流、Grade评分、Query改写)；大模型仅负责复杂意图规划与最终答案生成。
2. **硬编码退出条件与最大轮数限制**：强制设置max_iterations=2或max_retries=1，超过重试上限直接兜底输出。
3. **确定性逻辑与Agent决策混合**：高频规则直接写死在Python代码层，减少大模型决策开销。

## 4. 三大架构多维对比矩阵

| 评估维度 | 传统RAG(Naive) | Graph RAG | Agentic RAG |
|---------|-------------|-----------|-------------|
| 关注核心 | 局部文本相似度 | 知识组织方式(实体关系+社区摘要) | 检索控制流程(Agent决策+多工具编排) |
| 成本聚集阶段 | 前期低、运行时低 | 全部堆在建库期 | 全部转嫁到运行时 |
| 最擅长场景 | 局部事实查询 | 宏观归纳与复杂关联 | 复杂多步骤任务、跨多数据源 |
| 支持数据源 | 单一向量文本块 | 知识图谱(实体与关系) | 多源异构(向量库/SQL/Web/API/图谱) |
| 前期建库成本 | 极低(仅Embedding) | 极高(大量LLM抽取与总结) | 极低(同传统RAG) |
| 数据增量更新 | 极低(直接Upsert) | 极高(图结构破坏需重构) | 极低(直接Upsert) |
| 单次问答延迟 | 极快(1~3秒) | 中等(2~5秒) | 极慢(10~30秒+) |
| 单次问答费用 | 极低 | 中等 | 较高(多轮反思) |
| 系统稳定性 | 高(确定性代码) | 中等(依赖抽取质量) | 较低(死循环与路由失误风险) |

## 5. 终极形态：Agentic Graph RAG与选型决策树

两者并不冲突，而是"大脑与工具"的完美结合：
- Agent(LangGraph编排的调度器)充当大脑：负责理解意图、拆解任务、反思纠错。
- Graph RAG、向量库、SQL、Web充当工具箱：Agent根据需要主动调用相应工具。

落地选型决策树：
- 数据源单一且只需简单事实问答 → 方案一：传统混合RAG(向量+BM25+Reranker)
- 核心痛点是海量文档的宏观总结/多跳实体关联 → 方案二：优化版Graph RAG(核心实体图化+局部更新+混合检索降级)
- 需要跨多种数据源且允许一定延迟 → 方案三：Agentic RAG(LangGraph编排+大小模型协同+超时截断)
- 全都要 → 方案四：Agentic Graph RAG(终极形态)
