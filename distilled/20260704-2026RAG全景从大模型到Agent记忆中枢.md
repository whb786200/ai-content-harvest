## 架构设计要点

**数据入库流水线**: 原始文档→文档解析→文本清洗→切分→向量化→写入向量库
- 元数据至关重要: chunk_id, source, page, chapter, created_at, doc_type

**查询增强四手段**: 查询改写 / 多查询生成 / 问题分解 / HyDE(生成假设答案检索)

**混合检索**: 向量检索(语义) + BM25(关键词) → RRF融合排序
- 初始权重: 向量:BM25 = 0.7:0.3
- RRF公式: score(doc) = Σ 1/(k + rank + 1), k=60

**重排序**: Bi-Encoder快速召回 → Cross-Encoder精确重排；中文首选BGE-Reranker

## Agent记忆中枢

**Agentic RAG**: LLM自主判断召回是否足够、是否多轮检索、选择数据源、评估答案可靠性
基于ReAct: Think → Act → Observation → Think → Answer

**Self-RAG**: 自主判断是否需要检索、内容是否相关
**CRAG**: 召回不足时自动触发Web Search补充

**长上下文 vs RAG**: 趋势是RAG精拣 + 长上下文LM理解

## GraphRAG

解决传统RAG的Chunk间无显式关系问题：抽取实体关系→构建知识图谱→图遍历多跳查询
优势：关联推理、全局摘要、可解释性；代价：构建维护成本高、延迟更高

## 落地选型速查

| 组件 | 快速验证 | 生产级 |
|------|----------|--------|
| 文档解析 | PyMuPDF | Docling/MinerU(中文) |

| Embedding | BGE-M3 | text-embedding-3-small(API) |
| 向量库 | Chroma/FAISS | Qdrant/Milvus(大规模) |
| LLM | GPT-4o-mini | Qwen2.5-72B/DeepSeek-V3(中文) |
| 框架 | LlamaIndex | Dify(低代码)/FastGPT |

## 三阶段落地路径

| 阶段 | 周期 | 目标 |
|------|------|------|
| 快速验证 | 1-2周 | 跑通流程 |
| 效果优化 | 2-4周 | 70%→85%+ |
| 生产化 | 4-8周 | 真实用户 |

## 六大避坑

1. 不过早优化: 先跑通基础RAG再玩GraphRAG
2. 不忽视数据质量: 垃圾进垃圾出
3. 不一刀切Chunk: 不同文档不同参数
4. 不只靠向量: 精确词必须配合BM25
5. 不忘权限控制: 按角色过滤
6. 不过度依赖框架: 要看中间日志

> RAG 80%的问题是数据问题，不是技术问题。技术选型核心原则：匹配场景，简单优先。
