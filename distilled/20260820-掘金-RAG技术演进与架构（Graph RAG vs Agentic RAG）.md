# RAG技术演进与架构：Graph RAG vs Agentic RAG的深度对比与落地降本

> 来源：掘金 · 2026-08-20 · https://juejin.cn/post/7675686590932484137

---

## 核心主题

系统梳理RAG从Naive到Graph RAG与Agentic RAG的演进路径，核心洞察是"成本时空转移哲学"——Graph RAG将成本堆在建库期（重建库轻运行），Agentic RAG将成本堆在运行时（轻建库重运行）。两者并非对立而是"大脑与工具"关系：Agent充当大脑负责规划反思，Graph RAG/向量库/SQL/Web充当工具箱。终极形态是Agentic Graph RAG。

---

## 方法论框架

### 传统RAG三大核心硬伤

```
1. "只见树木不见森林" → 向量检索只命中局部片段，宏观归纳问题无法匹配
2. "一次性被动检索"  → 无论检索质量好坏都喂给LLM → 幻觉或拒答
3. "数据源单一"      → 只能处理非结构化文本，无法关联SQL/图谱/Web
```

### 成本时空转移哲学（核心洞察）

| 架构 | 成本聚集阶段 | 建库成本 | 运行时成本 |
|------|------------|---------|-----------|
| Graph RAG | 建库期(Indexing Time) | 极高（LLM抽取+社区摘要） | 低（预构建图遍历） |
| Agentic RAG | 运行时(Runtime/Query Time) | 极低（同传统RAG） | 高（多轮LLM推理Token） |

### 三大架构多维对比矩阵

| 维度 | 传统RAG | Graph RAG | Agentic RAG |
|------|---------|-----------|-------------|
| 关注核心 | 局部文本相似度 | 知识组织方式(实体关系+社区) | 检索控制流程(Agent决策) |
| 最擅长场景 | 局部事实查询 | 宏观归纳+复杂关联 | 复杂多步骤跨多数据源 |
| 前期建库成本 | 极低 | 极高 | 极低 |
| 增量更新 | 极低(Upsert) | 极高(图结构破坏需重构) | 极低(Upsert) |
| 单次问答延迟 | 1~3秒 | 2~5秒 | 10~30秒+ |
| 单次问答费用 | 极低 | 中等 | 较高(多轮反思) |
| 系统稳定性 | 高(确定性代码) | 中等(依赖抽取质量) | 较低(死循环风险) |

### Graph RAG四大降本方案

1. **非全量图化**：按Schema定向抽取核心实体，高价值文档才建图
2. **小模型NER+规则词典**：先用轻量NER+业务词典，仅必要时调LLM消歧
3. **局部子图更新**：新文档只更新受影响最小社区，分层缓存高频摘要
4. **混合检索动态分流**：默认向量+BM25+Reranker，仅全局/多跳才触发Graph引擎

### Agentic RAG四大核心模式

| 模式 | 核心 | 优势 |
|------|------|------|
| Router RAG | 动态路由分发到最合适数据源 | 降延迟 |
| Corrective RAG | 质量判定+自动重检索+网络搜索降级 | 纠错 |
| Self-RAG | 生成后反查引用源消除幻觉 | 防幻觉 |
| Multi-step Reasoning | 复合大问题拆解为子问题依次检索 | 复杂推理 |

### Agentic RAG降本三策略

1. **大小模型协同**：小模型负责Router分流/Grade评分/Query改写，大模型仅负责规划+最终生成
2. **硬编码退出条件**：max_iterations=2或max_retries=1，超限直接兜底输出
3. **确定性逻辑混合**：高频规则直接写死在Python代码层，减少LLM决策开销

### 落地选型决策树

```
数据源单一 + 简单事实问答 → 方案一：传统混合RAG(向量+BM25+Reranker)
海量文档宏观总结/多跳关联 → 方案二：优化版Graph RAG(核心图化+局部更新+混合降级)
跨多数据源 + 允许延迟     → 方案三：Agentic RAG(LangGraph+大小模型+超时截断)
全都要                    → 方案四：Agentic Graph RAG(终极形态)
```

| 模型协同 | 小模型(NER/路由) + 大模型(规划/生成) | 成本控制 |

## 关键洞察

1. **成本时空转移是选型的第一决策变量**：不是"哪个更好"而是"把巨大算力Token成本花在哪个阶段"——建库期还是运行时
2. **Graph RAG增量更新是最大痛点**：新增文档破坏图拓扑和社区划分，可能导致全量摘要重算——这是落地最大障碍
3. **Agentic RAG本质是"编排多工具的Agent"**：LangGraph状态图的循环自纠是关键能力，但也带来5-10x成本和死循环风险
4. **终极形态是Agentic Graph RAG**：Agent当大脑（理解/拆解/反思），Graph RAG/向量库/SQL/Web当工具箱——按需调用
5. **混合检索动态分流是Graph RAG降本关键**：80%+简单查询走向量+BM25，仅全局/多跳才触发图引擎
6. **max_iterations硬限制是Agentic RAG的保险丝**：强制设上限防止死循环和错误级联

## 金句

> "两者的本质差异在于把巨大的算力与Token成本花在哪个阶段：Graph RAG是'重建库、轻运行'，Agentic RAG是'轻建库、重运行'。"

> "Agent充当大脑，Graph RAG、向量库、SQL、Web充当工具箱——两者并非对立而是'大脑与工具'的完美结合。"

> "在线查询延迟极高：多次LLM往返，单次问答通常耗时10~30秒以上，Token是传统RAG的5~10倍。"

## 适用场景

- **RAG架构选型**：按数据源复杂度+延迟容忍度+预算选型（四方案决策树）
- **Graph RAG落地降本**：非全量图化+小模型NER+局部更新+混合分流
- **Agentic RAG工程化**：LangGraph编排+大小模型协同+硬编码退出+超时截断
- **企业知识库升级路径**：传统混合RAG → 按需Graph RAG → Agentic Graph RAG渐进演进
