# 2026 RAG全景：从大模型基座到Agent记忆中枢

> 来源：腾讯云开发者 · 2026-04-14 · https://cloud.tencent.com/developer/article/2654878

---

## 核心主题

RAG（检索增强生成）是一种思路，不是一项单一技术——本质是"在需要知识时动态检索，而不是把所有知识固化在模型里"。本文系统梳理RAG五代演进、架构设计要点、Agent记忆中枢（Agentic RAG/Self-RAG/CRAG）、GraphRAG，以及从文档解析到向量库的完整选型指南和三阶段落地路径。核心判断：**RAG 80%的问题是数据问题，不是技术问题**。

---

## 方法论框架

### RAG五代演进

| 代际 | 时期 | 核心特征 | 局限 |
|------|------|----------|------|
| 第一代 | 2020 | Facebook首提，端到端可训练 | 学术圈 |
| 第二代 | 2022-23 | Prompt Engineering+LangChain/LlamaIndex | 静态管道 |
| 第三代 | 2023-24 | Advanced RAG: Pre/During/Post三环节优化 | 仍为单次检索 |
| 第四代 | 2024 | Modular RAG: 模块化动态组合 | 模块间缺协调 |
| 第五代 | 2025+ | Agentic RAG: LLM自主决策检索，ReAct框架 | 延迟/成本更高 |

### RAG核心三步

```
Retrieval（检索） → Augmentation（增强） → Generation（生成）
     ↑                    ↑                      ↑
  向量库+BM25        拼接到Prompt          LLM生成答案
```

### 查询增强四手段

```
1. 查询改写 ──── 去口语化、补全指代
2. 多查询生成 ── 一问扩展3-5个子查询
3. 问题分解 ─── 复杂问题拆子问题
4. HyDE ─────── LLM生成假设答案，用答案去检索
```

### 混合检索 + 重排序

```
向量检索(语义, 权重0.7) + BM25(关键词, 权重0.3)
            ↓
      RRF融合排序: score(doc) = Σ 1/(k + rank + 1), k=60
            ↓
  Bi-Encoder大范围召回 → Cross-Encoder精确重排
  （中文首选: BGE-Reranker）
```

### Agent记忆中枢

| 模式 | 核心能力 | 适用场景 |
|------|----------|----------|
| Agentic RAG | LLM自主判断召回是否充分、多轮检索、选择数据源 | 复杂推理 |
| Self-RAG | 自主判断是否需要检索、内容是否相关 | 简单→复杂自适应 |
| CRAG | 召回不足时自动触发Web Search补充 | 知识库覆盖不足 |
| GraphRAG | 实体关系图谱+图遍历多跳查询 | 关联推理、全局摘要 |

### 长上下文 vs RAG 决策

```
长上下文: 无需检索，但成本极高、大海捞针
RAG:      超大规模知识库、强可溯源、频繁更新、成本可控
趋势:     RAG精拣 + 长上下文LM理解
```

## 工具链

| 环节 | 推荐工具 | 选型依据 |
|------|----------|----------|
| 文档解析 | PyMuPDF(轻量)/Docling(复杂排版)/Unstructured(多格式)/MinerU(中文) | 按文档复杂度选 |
| Chunking | 父子Chunk(小检索128,大返回512-1024) | 进阶推荐 |
| Embedding | BGE-M3(中文首选)/text-embedding-3-small(API)/BGE-large-zh(本地) | 按部署模式选 |
| 向量库 | Chroma/FAISS(验证) → pgvector(已有PG) → Qdrant(中小企业) → Milvus(大规模) → Pinecone(零运维) | 按规模选 |
| LLM | GPT-4o/Claude(最强) → GPT-4o-mini/Gemini Flash(平衡) → Qwen2.5-72B/DeepSeek(中文) → Qwen2.5-32B(本地) | 按场景选 |
| RAG框架 | LangChain(生态全)/LlamaIndex(专注RAG)/Haystack(企业级)/Dify(低代码)/FastGPT(知识库)/Coze(Agent) | 按团队能力选 |

### 三阶段落地路径

| 阶段 | 周期 | 目标 | 技术栈 |
|------|------|------|--------|
| 快速验证 | 1-2周 | 跑通流程 | PyMuPDF+Chroma+BGE-M3+GPT-4o-mini+LlamaIndex |
| 效果优化 | 2-4周 | 70%→85%+ | 评估集+查询改写+混合检索+重排序+Prompt优化 |
| 生产化 | 4-8周 | 真实用户 | 生产向量库+全链路日志+数据飞轮+监控 |

### 避坑清单

- 不过早优化：先跑通基础RAG再玩GraphRAG
- 不忽视数据质量：垃圾进垃圾出
- 不一刀切Chunk：不同文档不同参数
- 不只靠向量：精确词必须配合BM25
- 不忘权限控制：按角色过滤
- 不只看答案：要看召回质量
- 不过度依赖框架：要看中间日志

## 关键洞察

1. **RAG 80%的问题是数据问题**：文档解析质量、切分策略、元数据标注决定了上限，LLM只决定逼近上限的速度
2. **RAG是一种思路而非单一技术**：本质是"在需要知识时动态检索"——从第一代到第五代都在优化这个核心思路
3. **Agentic RAG是自然演进方向**：LLM自主判断召回是否充分→多轮检索→自我修正，基于ReAct框架
4. **长上下文不会取代RAG**：趋势是"RAG精拣+长上下文LM理解"的组合方案
5. **混合检索是生产标配**：向量(语义)+BM25(关键词)→RRF融合→Cross-Encoder重排
6. **技术选型核心原则：匹配场景，简单优先**——不过早优化、不忽视数据质量、不一刀切Chunk

- **RAG系统选型**：工具链表 → 按部署模式/规模/团队能力选择
- **Agentic RAG升级**：从Advanced RAG→Agentic RAG，引入自主检索决策
